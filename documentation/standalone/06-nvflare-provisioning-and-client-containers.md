# NVFlare Provisioning and Client Containers

## Current Datasource Runtime Model

Standalone client utilities use datasource environment values as host-side staging paths for local JSON files. Those files are copied into client containers under `/data/client/`. The running client does not use retired `DUALITY_FHIR_BASE_CONFIG.json` or retired `DUALITY_NVFLARE_FHIR_BASE_CONFIG`; it requests its datasource from the NVFlare server, which resolves the value through backend user settings.

See `09-local-datasource-staging-and-runtime-lookup.md` for the full current flow.

## NVFlare Provisioning Role

The standalone package provisions a local NVFlare environment so the SHARE frontend and backend can run local federated jobs against:

- one local NVFlare server container
- one or more local NVFlare client containers
- the backend job orchestration code
- the admin startup kit required by backend/admin-job submission logic

The generated NVFlare workspace is not intended to be hand-authored. It is created from `project.yml`, the resolved local host/IP, and the configured NVFlare ports.

The raw test data files and the generated NVFlare provisioned workspace may be omitted from lightweight zips. That is acceptable as long as the code, environment variables, and startup kit generation flow remain documented here.

## Project Configuration Files

Provisioning starts from:

```text
project.yml
```

The provisioning script writes a local variant next to it:

```text
project.local.yml
```

The local file is generated by `rewrite_project_for_local()` in `nvflare_stage/nvflare_install_and_provision.py`. It rewrites:

- the first participant block whose `type` is `server`
- that server participant's `name`
- that server participant's `fed_learn_port`
- that server participant's `admin_port`
- the dummy overseer `sp_end_point`

The host and ports come from:

| Environment variable | Default/source | Use |
| --- | --- | --- |
| `DUALITY_NVFLARE_HOST` | Seeded from `default.env.local`; changed from `auto` to the detected local IP by `main.py` startup | Server participant name and dummy overseer endpoint host. |
| `DUALITY_NVFLARE_FED_PORT` | `8002` | NVFlare federated learning port. |
| `DUALITY_NVFLARE_ADMIN_PORT` | `8003` | NVFlare admin port. |
| `DUALITY_NVFLARE_PROJECT_FILE` | `project.yml` | Source project file to rewrite and provision from. |
| `DUALITY_NVFLARE_WORKSPACE` | `./nvflare_workspace` | Provisioned workspace output directory. |
| `DUALITY_NVFLARE_ADMIN_NAME` | `admin@share.local` | Admin participant folder name to tar into `dist/admin_startup_kit.tar`. |

### `project.yml` participant definitions

`project.yml` defines one server, ten clients, and one admin.

| Participant | Type | Org | Notes |
| --- | --- | --- | --- |
| `127.0.0.1` | `server` | `site1` | Baseline server name before local rewriting. Uses `fed_learn_port: 8002` and `admin_port: 8003`. |
| `site1` | `client` | `site1` | Local client participant. |
| `site2` | `client` | `site2` | Local client participant. |
| `site3` | `client` | `site3` | Local client participant; the client container flow gives this site initiator-specific behavior. |
| `site4` through `site10` | `client` | matching site org | Defined in NVFlare project config even though only site1-site3 have default datasource entries in `default.env.local`. |
| `admin@share.local` | `admin` | `site1` | Project admin used to build the admin startup kit tar. |

The builder chain is:

| Builder | Purpose |
| --- | --- |
| `nvflare.lighter.impl.workspace.WorkspaceBuilder` | Creates the NVFlare workspace using `master_template.yml`. |
| `nvflare.lighter.impl.template.TemplateBuilder` | Applies NVFlare template processing. |
| `nvflare.lighter.impl.static_file.StaticFileBuilder` | Writes static startup files and configures the dummy overseer agent. |
| `nvflare.lighter.impl.cert.CertBuilder` | Generates participant certificates. |

The dummy overseer is configured with:

```text

```

```text
sp_end_point: 127.0.0.1:8002:8003
```

The local generated `project.local.yml` endpoint uses the detected or configured host, for example:

```text
sp_end_point: 192.168.0.29:8002:8003
```

## NVFlare Stage Walkthrough

The NVFlare stage is implemented in:

```text
nvflare_stage/nvflare_install_and_provision.py
```

The public entrypoint is:

```text
python3 main.py nvflare
```

The same `nvflare_run()` function is also called internally by the default setup flow when the Docker action requires provisioning.

### Stage flow

`run()` performs the following steps:

1. Load `.env.local` from the standalone root.
2. Delete and recreate `dist/` so the admin startup kit tar is refreshed.
3. Read `DUALITY_NVFLARE_HOST`, `DUALITY_NVFLARE_FED_PORT`, and `DUALITY_NVFLARE_ADMIN_PORT`.
4. Read `DUALITY_NVFLARE_PROJECT_FILE`, defaulting to `project.yml`.
5. Read `DUALITY_NVFLARE_WORKSPACE`, defaulting to `nvflare_workspace`.
6. Check whether the workspace already appears provisioned by looking for:

   ```text
   <DUALITY_NVFLARE_WORKSPACE>/duality_nvflare/prod_00
   ```

7. If that directory exists, skip the provisioning command and reuse the existing workspace.
8. If that directory does not exist, install/use NVFlare as needed, write `project.local.yml`, and provision the workspace.
9. Locate the admin participant folder under the workspace.
10. Create `dist/admin_startup_kit.tar` containing the admin participant directory.
11. Write the absolute admin tar path back into `.env.local` as `DUALITY_ADMIN_TAR`.
12. Print the resolved server host, ports, workspace path, and admin tar path.

### Skip behavior

Provisioning is skipped when this directory already exists:

```text
<workspace>/duality_nvflare/prod_00
```

The admin tar is still rebuilt from the existing workspace, and `DUALITY_ADMIN_TAR` is still updated in `.env.local`.

### Local install behavior

On non-Windows systems, the script checks whether the Python package `nvflare` can be imported. If it cannot, it attempts:

```text
python -m pip install nvflare==2.7.2
```

Provisioning then tries these local command forms in order where available:

```text
nvflare provision -p <project.local.yml> -w <workspace>
provision -p <project.local.yml> -w <workspace>
python -m nvflare.cli provision -p <project.local.yml> -w <workspace>
```

The local provisioning timeout defaults to:

```text
DUALITY_NVF_LOCAL_TIMEOUT_SECS=600
```

### Windows/WSL behavior

On Windows, the script skips local Python provisioning attempts and uses WSL. It checks WSL with:

```text
wsl --status
```

Then it runs a root WSL command that:

1. Changes into the Windows working directory through the `/mnt/<drive>/...` path.
2. Runs `apt-get update`.
3. Installs `python3-venv` and `python3-pip`.
4. Creates `/root/.nvf_venv`.
5. Installs `nvflare==2.7.2` into that venv.
6. Runs:

   ```text
   /root/.nvf_venv/bin/nvflare provision -p <project.local.yml> -w <workspace>
   ```

The WSL provisioning timeout defaults to:

```text
DUALITY_NVF_WSL_TIMEOUT_SECS=900
```

### Admin startup kit tar behavior

The admin tar is always written to:

```text
dist/admin_startup_kit.tar
```

The tar contains the admin folder name as the archive root. In the current package, the tar contains entries such as:

```text
admin@share.local/
admin@share.local/local/resources.json.default
admin@share.local/local/signature.json
admin@share.local/startup/client.crt
admin@share.local/startup/client.key
admin@share.local/startup/fed_admin.json
admin@share.local/startup/fl_admin.sh
admin@share.local/startup/rootCA.pem
admin@share.local/startup/signature.json
```

Before writing the tar, the script ensures `local/` exists, makes `fl_admin.sh` executable when present, and normalizes CRLF line endings in `fl_admin.sh`.

The backend Dockerfile copies this tar into the backend image at:

```text
/kits/admin_startup_kit.tar
```

The backend Compose service sets:

```text
DUALITY_ADMIN_TAR=/kits/admin_startup_kit.tar
```

## NVFlare Workspace

The active workspace path is controlled by:

```text
DUALITY_NVFLARE_WORKSPACE=./nvflare_workspace
```

Although the placeholder listed `nvflare_stage/nvflare_workspace/`, the current environment template points to:

```text
./nvflare_workspace
```

The expected provisioned root is:

```text
./nvflare_workspace/duality_nvflare/prod_00
```

The main Compose stack mounts this host directory:

```text
../nvflare_workspace
```

into both the backend and NVFlare server containers at:

```text
/home/ubuntu/nvflare/workspace
```

Inside containers, the server base path is:

```text
/home/ubuntu/nvflare/workspace/duality_nvflare/prod_00
```

The backend service sets:

```text
DUALITY_NVFLARE_WORKSPACE=/home/ubuntu/nvflare/workspace/duality_nvflare/prod_00
DUALITY_NVFLARE_SUBMITTED_JOBS_LOCATION=/home/ubuntu/nvflare/workspace/duality_nvflare/prod_00/${DUALITY_NVFLARE_HOST}/submitted_jobs
```

The NVFlare server service sets:

```text
NVFLARE_SERVER_BASE=/home/ubuntu/nvflare/workspace/duality_nvflare/prod_00
DUALITY_NVFLARE_HOST=${DUALITY_NVFLARE_HOST}
```

The backend and NVFlare server share this workspace mount so backend job submission and server startup see the same provisioned files.

### Server Dockerfile behavior

`docker_stage/nvflare.Dockerfile` builds from `ubuntu:24.04` and installs:

- Python 3
- `python3-venv`
- `python3-pip`
- shell/network utilities
- build tools
- `libgomp1`
- OpenSSL headers
- `liboqs` from `https://github.com/open-quantum-safe/liboqs`

The image does not bake the `duality_nvflare_lib` wheel into a layer; the container start command installs the bundled snapshot wheel from the read-only `/opt/duality/local_wheels` mount, and submitted jobs only verify that it is installed.

At container startup it:

1. Exports `LD_LIBRARY_PATH` and `OQS_INSTALL_PATH`.
2. Creates a Python venv at `/opt/nvflare/.venv`.
3. Installs/upgrades `pip`.
4. Installs stable runtime dependencies required by submitted jobs.
5. Ensures `NVFLARE_SERVER_BASE` exists.
6. Chooses the startup directory. It first tries:

   ```text
   $NVFLARE_SERVER_BASE/$DUALITY_NVFLARE_HOST/startup
   ```

   If that does not exist, it finds the first `startup` directory under the server base.

7. Removes stale `daemon_pid.fl` files.
8. Runs `stop_fl.sh` if it exists, suppressing errors and waiting 10 seconds.
9. Runs `start.sh`.
10. Keeps the container alive with `tail -f /dev/null`.

This startup sequence is important because NVFlare 2.7.2 can leave stale daemon state behind between local rebuilds.

## Client Container Flow

Client containers are not part of `docker_stage/docker-compose.yml`. They are created independently through:

```text
python3 main.py client --site <site>
```

or from an existing tar:

```text
python3 main.py client --tar-file ./dist/client_site1_startup_kit.tar
```

There is also a direct utility entrypoint:

```text
python3 client_utils/create_client.py --site <site>
```

The `main.py client` command is the preferred standalone path because it runs through the same environment seeding and argument forwarding as the rest of the orchestrator.

### Client command arguments

| Argument | Required | Purpose |
| --- | --- | --- |
| `--site <site>` | Mutually exclusive with `--tar-file` | Build a startup kit tar from the provisioned workspace participant folder and then build/start the client container. |
| `--tar-file <path>` | Mutually exclusive with `--site` | Use an existing `client_<site>_startup_kit.tar`; the site is inferred from the filename. |
| `--tar-kit` | Optional, only valid with `--site` | Only create `dist/client_<site>_startup_kit.tar` and optionally ensure the MySQL client record. Does not build/start a container. |
| `--compose-file <path>` | Optional | Compose template path. Defaults to `client_utils/docker-compose.client-template.yml`. |
| `--project <name>` | Optional | Compose project name for client resources. Defaults to `duality-client`. |
| `--env-file <path>` | Optional global argument through `main.py`; direct utility also supports it | Load a non-default env file. Defaults to `.env.local`. |
| `--no-cache` | Optional | Build the site's client image, and its results-agent image when one applies, without the layer cache before starting them. |
| `--stop` | Optional, only valid with `--site` | Stop the site's client container and any companion results-agent container, then exit. |

`main.py` has a special early branch for `client` so the client utility receives its own arguments directly. This avoids the main parser interfering with the client utility's mutually exclusive `--site`/`--tar-file` behavior.

### `--site` flow

When called with `--site`, `client_utils/create_client.py` performs this flow:

1. Load `.env.local` or the provided env file without overwriting values already present in `os.environ`.
2. Check Docker access using `docker info`.
3. Read `DUALITY_NVFLARE_WORKSPACE`, defaulting to `standalone/nvflare_workspace` if not set.
4. Search recursively under the workspace for a participant directory whose folder name exactly matches the requested site.
5. If the participant directory is not found, exit with an error.
6. Create `dist/client_<site>_startup_kit.tar` from that participant directory.
7. Collect datasource settings for that site from environment variables.
8. Verify `client_utils/client.Dockerfile` and `client_utils/docker-compose.client-template.yml` exist, plus `client_utils/client-results-agent/Dockerfile` for every site except `site3`.
9. Call backend `/user/role` to initialize database/tables where possible.
10. Ensure the MySQL client record exists.
11. Stage local datasource JSON files into `client_utils/injected_datasources/`.
12. Stage an optional local `duality_nvflare_lib-*.whl` into `client_utils/local_wheels/`.
13. Create the site results directory: `standalone/job-results/<site>` for regular sites, `standalone/job-results` for `site3`.
14. Derive the site's results-agent port for regular sites.
15. Render a temporary per-site Compose file by changing the service keys from `client` and `results-agent` to `client-<site>` and `results-agent-<site>`.
16. Remove any existing containers named `duality-client-<site>` and `duality-client-results-<site>`.
17. Run, including `results-agent-<site>` for every site except `site3`:

   ```text
   docker compose -p duality-client -f <temporary-compose-file> up -d --build client-<site> [results-agent-<site>]
   ```

18. Delete temporary build artifacts after the Compose command finishes:

   ```text
   client_utils/injected_datasources/
   client_utils/docker-compose.client.<site>.<pid>.yml
   ```

### `--tar-file` flow

When called with `--tar-file`, the utility:

1. Validates the tar file exists.
2. Infers the site from a filename matching:

   ```text
   client_<site>_startup_kit.tar
   ```

3. Skips searching the workspace for the participant folder.
4. Runs the same datasource staging, MySQL registration, Compose rendering, container replacement, and build/start behavior as the `--site` path.

### `--tar-kit` flow

When called with:

```text
python3 main.py client --site site1 --tar-kit
```

The utility:

1. Finds the participant folder under the workspace.
2. Writes `dist/client_site1_startup_kit.tar`.
3. Prompts whether to create/ensure the client entry in MySQL.
4. If accepted, calls `ensure_client_registered(site)`.
5. Exits without building or starting a client container.

In non-interactive input, the yes/no prompt uses the default value. For this prompt the default is yes.

| Concept | Pattern/example |
| --- | --- |
| CLI site argument | `site1`, `site2`, `site3` |
| NVFlare participant folder | `<DUALITY_NVFLARE_WORKSPACE>/.../<site>` |

| Docker container names | `duality-client-<site>`, `duality-client-results-<site>` |
| MySQL `nvflare_clients.client_name` | `<site>` |
| MySQL user for most sites | `client_<site>` |
| MySQL user for `site3` | `initiator` |
| Client logs command shown after startup | `docker logs -f duality-client-<site>` |
| Results agent logs command shown after startup | `docker logs -f duality-client-results-<site>` |

Every site sets `CLIENT_JOB_SAVE_LOCATION=/job-results` and `ENABLE_JOB_RESULTS_SYMLINK=true`. The special `site3` behavior is implemented in `create_client.py`:

- `site3` maps to the existing user `initiator`.
- `site3` uses the shared `standalone/job-results` directory, while other sites get an isolated `standalone/job-results/<site>` directory so the same job and workflow IDs cannot overwrite each other's `local_results.json` files.
- `site3` starts no companion results agent, so it also has no published results port.
- After startup, `site3` additionally has its model files copied into place by `copy_site3_model_files()`.

## Client MySQL Registration

The `clientdb` command only ensures the database mapping for a site:

```text
python3 main.py clientdb --site site1
```

`cmd_clientdb()` loads the env file, pings backend `/user/role`, then calls `ensure_client_registered(site)`.

`ensure_client_registered(site)` connects to MySQL using:

| Variable | Default in code/template context | Purpose |
| --- | --- | --- |
| `DUALITY_MYSQL_HOST` | `localhost` | MySQL host. In container DB mode, `.env.local` uses host port access for local scripts. |
| `DUALITY_MYSQL_PORT` | `3306` in code, `3307` in template | MySQL port. |
| `DUALITY_MYSQL_USER` | `root` in code, `duality` in template | Database user. |
| `DUALITY_MYSQL_PASSWORD` | empty in code, configured in template | Database password. |
| `DUALITY_MYSQL_DB` | `duality_dev` | Database name. |

For most sites, it upserts:

| Table | Values |
| --- | --- |
| `defined_roles` | `name='client'`, `description='NVFLARE client role'` |
| `users` | `username='client_<site>'`, `password_hash='DISABLED'`, `role_id=<client role id>` |
| `nvflare_clients` | `client_name=<site>`, `user_id=<user id>`, `description='Auto-created for <site>'` |

For `site3`, it expects an existing user:

```text
initiator
```

If `initiator` does not exist, registration for `site3` fails.

All upserts use `ON DUPLICATE KEY UPDATE id=LAST_INSERT_ID(id)` patterns so rerunning the command returns or updates existing rows instead of creating duplicates.

## Datasource Injection

Client datasource configuration is environment-driven.

The preferred grouped/ungrouped naming pattern is:

```text
DUALITY_CLIENT_<SITE>_DATASOURCE_<PROJECT_ID>=<value>
DUALITY_CLIENT_<SITE>_DATASOURCE_<PROJECT_ID>_<DATASOURCE_GROUP_ID>=<value>
```

Examples from `default.env.local`:

```text
DUALITY_CLIENT_SITE3_DATASOURCE_1=nvflare_stage/data/Survivability_FHIR_Data_part1.json
DUALITY_CLIENT_SITE1_DATASOURCE_1=nvflare_stage/data/Survivability_FHIR_Data_part2.json
DUALITY_CLIENT_SITE2_DATASOURCE_1=nvflare_stage/data/Survivability_FHIR_Data_part3.json

DUALITY_CLIENT_SITE3_DATASOURCE_2_1=nvflare_stage/data/Biomarker_MSKChord_FHIR_Data_training_bundle.json

DUALITY_CLIENT_SITE1_DATASOURCE_2_1=nvflare_stage/data/Biomarker_MSKChord_FHIR_Data_testing_bundle_site1.json

DUALITY_CLIENT_SITE2_DATASOURCE_2_1=nvflare_stage/data/Biomarker_MSKChord_FHIR_Data_testing_bundle_site2.json
```

There is also a legacy single-project fallback:

```text
DUALITY_CLIENT_<SITE>_DATASOURCE=<value>
```

If no preferred matches are found but this fallback exists, the code treats it as project `1`.

### Datasource parsing rules

`create_client.py` scans environment variables using a site-specific uppercase prefix. For `site1`, the prefix is:

```text
DUALITY_CLIENT_SITE1_DATASOURCE_
```

The suffix after that prefix is parsed as:

| Suffix shape | Meaning | Example |
| --- | --- | --- |
| `<PROJECT_ID>` | Ungrouped datasource for one project | `DUALITY_CLIENT_SITE1_DATASOURCE_1` |
| `<PROJECT_ID>_<DATASOURCE_GROUP_ID>` | Datasource for one project and one datasource group | `DUALITY_CLIENT_SITE1_DATASOURCE_2_1` |

Grouped and ungrouped configuration cannot be mixed for the same project. If a project has both `DUALITY_CLIENT_SITE1_DATASOURCE_2=...` and `DUALITY_CLIENT_SITE1_DATASOURCE_2_1=...`, the utility exits with an error.

Entries are sorted by numeric project ID, numeric datasource group ID, and raw suffix.

### Remote FHIR URL handling

A value is treated as a remote datasource when it parses as `http` or `https`, has a network location, and its path does not end in `.json`.

Remote datasource values are stored in backend user datasource settings and are not copied into the Docker build context.

Example:

```text
DUALITY_CLIENT_SITE1_DATASOURCE_1=https://example-fhir-server.test/fhir
```

### Local JSON handling

A value is treated as a local datasource when it is not a remote FHIR URL. Relative paths are resolved from the standalone repo root.

Example:

```text
DUALITY_CLIENT_SITE1_DATASOURCE_2_1=nvflare_stage/data/Biomarker_MSKChord_FHIR_Data_testing_bundle_site1.json
```

For local JSON values, the utility:

1. Expands `~`.
2. Resolves relative paths from the standalone root.
3. If the target `.json` is missing, checks for a same-name `.zip` next to it.
4. If a matching zip exists, extracts the matching JSON file or a single JSON member.
5. Copies the JSON file into:

   ```text
   client_utils/injected_datasources/
   ```

6. Fails if the local file does not exist after normalization/extraction.
7. Fails if two staged local datasources have the same filename.

The client Dockerfile copies staged datasources into the image at:

```text
/data/client/
```

## Runtime Datasource Lookup

Client containers no longer receive a generated FHIR base config file. The only datasource material copied into the client image is local JSON data under:

```text
/data/client/
```

At job runtime, `analytics_executor.py` reads `custom/filters.json`, sends `project_id` and `datasource_group_id` to the NVFlare server on `duality.datasource.lookup`, and receives the datasource returned by backend `/clients/datasource/source`.

For local JSON datasources, backend should return `/data/client/<filename>.json`. For FHIR server datasources, backend should return an `http://` or `https://` URL ending in `/fhir`.

## Client Compose Generation

The source template is:

```text
client_utils/docker-compose.client-template.yml
```

The template defines two service keys named:

```text
client
results-agent
```

Because Docker Compose does not support variable substitution in service names, `render_compose_for_site_temp()` rewrites both service keys to:

```text
client-<site>
results-agent-<site>
```

and writes a temporary file next to the template:

```text
client_utils/docker-compose.client.<site>.<pid>.yml
```

If either rewrite does not match, the script exits with status `14`. That temporary file is deleted after the client build/start command completes.

The launcher then starts `client-<site>` for every site, plus `results-agent-<site>` for every site except the initiator site `site3`. The results agent serves that site's local results to the browser; `site3` does not need one because the backend already exposes the shared `job-results` directory.

### Generated client Compose example

For `site1`, the temporary rendered file becomes:

```yaml
services:
  client-site1:
    build:
      context: .
      dockerfile: client.Dockerfile
    platform: linux/amd64
    container_name: "duality-client-site1"
    environment:
      NVFLARE_VENV_DIR: /opt/nvflare/.venv
      NVFLARE_SERVER_BASE: /home/ubuntu/nvflare/workspace/duality_nvflare/prod_00
      DUALITY_NVFLARE_HOST: "site1"
      NVFLARE_SERVER_TAR_PATH: /kits/client_startup_kit.tar
      DUALITY_NVFLARE_JOB_SAVE_LOCATION: "/job-results"
      DUALITY_ENABLE_JOB_RESULTS_SYMLINK: "true"
      DUALITY_NVFLARE_LIB_UPDATE_DISABLED: ""
      DUALITY_HOST_UID: "1000"
      DUALITY_HOST_GID: "1000"
    volumes:
      - "<absolute path>/dist/client_site1_startup_kit.tar:/kits/client_startup_kit.tar:ro"
      - "<absolute path>/standalone/job-results/site1:/job-results"
      - "./local_wheels:/opt/duality/local_wheels:ro"
    restart: unless-stopped

  results-agent-site1:
    build:
      context: ./client-results-agent
      dockerfile: Dockerfile
    container_name: "duality-client-results-site1"
    environment:
      DUALITY_CLIENT_SITE: "site1"
      DUALITY_NVFLARE_JOB_SAVE_LOCATION: /job-results
      DUALITY_UI_ORIGINS: ""
    volumes:
      - "<absolute path>/standalone/job-results/site1:/job-results:ro"
    ports:
      - "127.0.0.1:8089:8088"
    restart: unless-stopped

networks:
  default:
    name: "duality_default"
    external: true
```

`DUALITY_HOST_UID` and `DUALITY_HOST_GID` show the launching host user's IDs, and are blank on hosts without `os.getuid`. The published results-agent port is `DUALITY_CLIENT_RESULTS_BASE_PORT` (default `8088`) plus the site number, so `site1` publishes `8089` and `site2` publishes `8090`, always bound to `127.0.0.1`.

For `site3`, the generated file is interpolated the same way, but only `client-site3` is started, and its results directory is the shared `standalone/job-results` rather than a per-site subdirectory.

## Client Dockerfile Behavior

`client_utils/client.Dockerfile` builds from `ubuntu:24.04` and installs the same base operating-system/runtime pieces used by the NVFlare server image:

- Python 3
- `python3-venv`
- `python3-pip`
- shell/network utilities
- build tools
- `libgomp1`
- OpenSSL headers
- `liboqs`

It copies build-context artifacts prepared by `create_client.py`:

| Source in `client_utils/` build context | Image path | Purpose |
| --- | --- | --- |
| `injected_datasources/` | `/data/client/` | Local JSON datasource files used by the client runtime. |

At container startup it:

1. Exports `LD_LIBRARY_PATH` and `OQS_INSTALL_PATH`.
2. Creates the venv at `/opt/nvflare/.venv`.
3. Installs/upgrades `pip`.
4. Installs stable runtime dependencies required by submitted jobs.
5. Installs the bundled `duality_nvflare_lib-0+phase1.snapshot-py3-none-any.whl` from `/opt/duality/local_wheels`; a missing local wheel is an error rather than a registry fallback.
6. Clears and recreates the client workspace base.
7. Extracts `/kits/client_startup_kit.tar` into:

   ```text
   /home/ubuntu/nvflare/workspace/duality_nvflare/prod_00
   ```

8. Makes shell scripts executable.
9. Normalizes CRLF line endings in shell scripts.
10. When `DUALITY_ENABLE_JOB_RESULTS_SYMLINK` is `true`, which the launcher sets for every site, replaces the participant `job-results` folder with a symlink to `/job-results`.
11. Changes to the participant startup directory.
12. Runs `start.sh`.
13. Keeps the container alive with `tail -f /dev/null` even if `start.sh` exits non-zero because the command includes `./start.sh || true`.

## Runtime Wheel Handling

The public NVFlare server and client containers use the wheel bundled with the checkout.
The launcher stages `duality_nvflare_lib-0+phase1.snapshot-py3-none-any.whl` into the
local-wheel mount and the container installs it locally. Submitted analytical jobs do
not contact GitLab or any package index to update `duality_nvflare_lib`; the job wrappers
only require/import the already-installed snapshot.

The public standalone redeploy command is:

```text
python3 main.py wheel
```

The command rebuilds/relaunches the main NVFlare service and redeploys already-running
clients using the bundled snapshot wheel.

## Fresh Re-Provisioning Procedure

Use this when the NVFlare host/IP, participant list, certificates, ports, or startup kits are stale.

1. Stop the main stack and client containers. From the standalone root:

   ```text
   docker rm -f duality-nvflare duality-backend frontend duality-mysql
   docker ps -a --format "{{.Names}}" | grep '^duality-client-' | xargs -r docker rm -f
   ```

2. Delete the generated workspace and startup kit outputs:

   ```text
   rm -rf nvflare_workspace
   rm -rf dist
   ```

3. Ensure `default.env.local` contains the desired host/port/project settings. `main.py` currently reseeds `.env.local` from `default.env.local` at startup, so durable changes belong in the template unless that behavior is changed.

4. Run provisioning:

   ```text
   python3 main.py nvflare
   ```

5. Rebuild/start the main stack through the default flow or UI:

   ```text
   python3 main.py
   ```

   or:

   ```text
   python3 main.py ui
   ```

6. Recreate client containers:

   ```text
   python3 main.py client --site site1
   python3 main.py client --site site2
   python3 main.py client --site site3
   ```

7. Verify the main server and clients are running:

   ```text
   docker ps --format "{{.Names}}  {{.Status}}"
   ```

## Safe Client Rebuild Procedure

Use this when staged local datasource files or startup kit content changed for one site.

```text
python3 main.py client --site site1
```

The client flow automatically removes the existing `duality-client-site1` container before rebuilding it. It does not remove the main MySQL volume or the main NVFlare server container.

For all currently running client containers, use the UI option:

```text
[8] Rebuild ALREADY RUNNING client containers
```

or run the redeploy workflow when the NVFlare server/client containers should be refreshed:

```text
python3 main.py wheel
```

## Troubleshooting Notes

### Workspace not found for client

Error pattern:

```text
Could not find client folder for '<site>' under workspace: <workspace>
```

Check that:

- `python3 main.py nvflare` has run successfully
- `DUALITY_NVFLARE_WORKSPACE` points to the same workspace used during provisioning
- the requested site exists in `project.yml`
- the provisioned workspace was not omitted or deleted

### No datasource configuration found

Error pattern:

```text
No datasource configuration found for site '<site>'.
```

Add either:

```text
DUALITY_CLIENT_<SITE>_DATASOURCE_<PROJECT_ID>=<remote-or-local-value>
```

or:

```text
DUALITY_CLIENT_<SITE>_DATASOURCE_<PROJECT_ID>_<DATASOURCE_GROUP_ID>=<remote-or-local-value>
```

For local JSON files, ensure the file exists or that a same-name `.zip` exists and contains the expected JSON.

### `site3` registration fails

`site3` maps to the existing user `initiator`. If that user has not been created by backend/login initialization, `ensure_client_registered('site3')` fails.

Run the backend stack, then rerun:

```text
python3 main.py clientdb --site site3
```

or:

```text
python3 main.py client --site site3
```

### Wheel command refuses to run

The wheel command requires both:

- the main `nvflare` container running
- at least one running client container named `duality-client-<site>`

Start the main stack and at least one client before running:

```text
python3 main.py wheel
```
