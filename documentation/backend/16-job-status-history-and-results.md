## Runtime Concepts

There are two related job identifiers in this backend:

| Identifier | Source | Stored In | Used By |
| --- | --- | --- | --- |
| Job runner ID | Generated by `JobRunnerService` before the background task starts. | `job_runner_log.uuid`, `nvflare_jobs.job_runner_id` | `/jobs/status`, websocket status streams, live progress logs, mapping a submitted request to one or more NVFlare jobs. |
| NVFlare assigned ID | Parsed from the `submit_job` admin command output after NVFlare accepts a job. | `nvflare_jobs.nvflare_assigned_id` | `/jobs/info`, `/jobs/results`, `/jobs/function/config`, `/jobs/results/mapping`, `/nvflare/jobs/history`, result directory lookup. |

The frontend receives the job runner ID immediately from `POST /nvflare/jobs/submit` as `job_id`. Live status endpoints poll or stream against that job runner ID. Result endpoints use the NVFlare assigned ID once it is available through status enrichment, history, or job info.

## Database Tables

### `job_runner_log`

`job_runner_log` is the live task-runner status table.

| Column | Type | Purpose |
| --- | --- | --- |
| `uuid` | `VARCHAR(36)` primary key | Job runner ID generated by `JobRunnerService`. |
| `status` | `VARCHAR(255)` | Current task-runner status. Written by `JobStatusWriter.log()` when a status is supplied. |
| `log` | `MEDIUMTEXT` | Timestamped accumulated log text. Each call appends a new line. |
| `create_date` | `DATETIME` | Row creation time. |
| `update_date` | `DATETIME` | Last status/log update time. |

Indexes:

| Index | Columns | Purpose |
| --- | --- | --- |
| `PRIMARY` | `uuid` | One live log row per job runner ID. |
| `idx_create_date` | `create_date DESC` | Supports recent-log ordering. |
| `idx_update_date` | `update_date` | Supports status freshness checks. |

`JobStatusWriter.log()` uses `INSERT ... ON DUPLICATE KEY UPDATE`, so the first write creates the row and later writes append log text and optionally replace the current status.

## Status Writer Behavior

`JobStatusWriter` is initialized with the job runner ID. It opens a MySQL connection immediately and writes to `job_runner_log`.

`log(log_message, status=None)` behavior:

1. Ignores empty messages.
2. Adds a UTC ISO timestamp prefix to the log line.
3. Checks whether the current row has status `STOP`.
4. If status is `STOP`, appends a final log line, commits it, and terminates the process with `os._exit(0)`.
5. Inserts the row if missing.
6. Appends the log line to `log` on every call.
7. Updates `status` only when a status argument is supplied.
8. Updates `update_date` on every write.

`safe_status_update()` prints the same status/message to stdout and then delegates to `JobStatusWriter.log()` when a writer is available.

## Live Status Retrieval

`JobStatusRetriever.get_status_by_uuid(uuid)` reads `job_runner_log` by job runner ID and enriches the row with NVFlare job information.

When a log row exists, it also queries `nvflare_jobs` where `job_runner_id = uuid` and adds:

| Field | Source | Purpose |
| --- | --- | --- |
| `referenced_by` | `nvflare_jobs.nvflare_assigned_id` | List of NVFlare assigned IDs created by the job runner task. |
| `run_duration` | First non-empty `nvflare_jobs.run_duration` | Runtime duration for frontend display. |
| `nvflare_jobs` | `nvflare_jobs` plus `nvflare_job_functions` | Detailed child job list with internal ID, NVFlare assigned ID, run duration, and function names. |
| `functions` | Distinct function names linked to all referenced NVFlare jobs | Summary function list. |

If no status row exists, route response building returns a default queued payload.

## `POST /jobs/status`

### Purpose

Polling endpoint for current live status by job runner ID.

### Request

```json
{
  "job_id": "6d94567b-04e2-4df0-bc10-d0b1a1f4d09f"
}
```

### Success Response

If a status row exists:

```json
{
  "job_id": "6d94567b-04e2-4df0-bc10-d0b1a1f4d09f",
  "status": "Broadcasting NVFlare Job",
  "log": [
    "[2026-04-28T19:18:00+00:00] NVFlareJobRunner: Job broadcasted successfully"
  ],
  "last_update": "2026-04-28T19:18:00",
  "functions": ["STAT_ANALYTICS"],
  "referenced_by": ["96b6f63e-0292-4f0e-bb64-a03b926b10bc"],
  "run_duration": "00:01:32"
}
```

If no row exists yet:

```json
{
  "job_id": "6d94567b-04e2-4df0-bc10-d0b1a1f4d09f",
  "status": "QUEUED",
  "log": [],
  "last_update": "None",
  "functions": []
}
```

### Status Codes

| Status | Behavior |
| --- | --- |
| `200` | Status payload returned. |
| `400` | Exception while retrieving status. Response includes traceback lines in `log`. |

### Backend Calls

1. `request.json()` parses the body.
2. `JobStatusRetriever.get_status_by_uuid(job_id)` reads `job_runner_log` and related `nvflare_jobs` rows.
3. `_build_job_status_response_body()` normalizes the response and removes non-JSON float values through `sanitize_json_values()`.
4. The retriever is closed in `finally`.

### Tables Read

| Table | Use |
| --- | --- |
| `job_runner_log` | Live status/log row by UUID. |
| `nvflare_jobs` | NVFlare IDs and run duration associated with the runner UUID. |
| `nvflare_job_functions` | Function links for each referenced NVFlare job. |
| `defined_functions` | Function names. |

## Direct Websocket Status: `WEBSOCKET /jobs/status/ws/{job_id}` and `/jobs/status/ws/local/{job_id}`

### Purpose

Streams the same status body used by `/jobs/status`, but only sends a status message when content changes. It also sends heartbeat messages while the status is unchanged.

Both routes are bound to the same handler.

### Client Connection

The client opens a websocket using the job runner ID in the path.

```text
/jobs/status/ws/6d94567b-04e2-4df0-bc10-d0b1a1f4d09f
/jobs/status/ws/local/6d94567b-04e2-4df0-bc10-d0b1a1f4d09f
```

### Outbound Status Message

```json
{
  "type": "job_status",
  "message_id": "70ec5c0f44dd4cf18a7d510489e03b1e",
  "requires_ack": true,
  "job_id": "6d94567b-04e2-4df0-bc10-d0b1a1f4d09f",
  "status": "Processing",
  "log": ["[2026-04-28T19:18:00+00:00] Job is processing"],
  "last_update": "2026-04-28T19:18:00",
  "functions": ["STAT_ANALYTICS"]
}
```

### Outbound Heartbeat Message

```json
{
  "type": "heartbeat",
  "message_id": "2a7f4f68efbf42a1af4e6c98e8837c44",
  "requires_ack": true,
  "job_id": "6d94567b-04e2-4df0-bc10-d0b1a1f4d09f"
}
```

### Required Client Acknowledgement

Each outbound websocket message requires an acknowledgement within 5 seconds.

```json
{
  "type": "ack",
  "message_id": "70ec5c0f44dd4cf18a7d510489e03b1e"
}
```

### Runtime Constants

| Constant | Value | Use |
| --- | --- | --- |
| `JOB_STATUS_WS_POLL_INTERVAL_SECONDS` | `0.5` | Database polling interval. |
| `JOB_STATUS_WS_ACK_TIMEOUT_SECONDS` | `5.0` | Time allowed for frontend acknowledgement. |
| `JOB_STATUS_WS_HEARTBEAT_INTERVAL_SECONDS` | `10.0` | Heartbeat interval when status payload is unchanged. |

### Close Behavior

The handler breaks the stream when the status value is `DONE` or `FAILURE` after uppercasing. It also closes the websocket on frontend disconnect, acknowledgement timeout, or an internal exception.

## API Gateway Websocket Bridge

The backend also exposes HTTP routes intended to be called by API Gateway websocket integrations. These routes maintain in-memory connection state and use `boto3` `apigatewaymanagementapi` to post messages back to connected clients.

### Shared Behavior

Connection state is stored in the process-level `_ACTIVE_API_GATEWAY_CONNECTIONS` dictionary with an `asyncio.Lock`. Each state entry contains:

| Field | Purpose |
| --- | --- |
| `connection_id` | API Gateway connection ID. |
| `job_id` | Job runner ID being streamed. |
| `management_endpoint` | API Gateway Management API endpoint used for posting responses. |
| `stop_event` | Stops the background stream loop. |
| `task` | Background stream task. |
| `pending_ack_message_id` | Message currently waiting for acknowledgement. |
| `pending_ack_event` | Async event released by the ack route. |

The management endpoint is derived from `domainName` and `stage` when present, or from the hardcoded websocket URL fallback `wss://ws.example.org/prod`.

### `POST /jobs/status/ws/connect`

Registers an API Gateway connection and starts a background status stream.

Request can include values at the top level, in `body`, in `queryStringParameters`, or in common API Gateway request-context fields.

```json
{
  "requestContext": {
    "connectionId": "abc123",
    "domainName": "ws.example.org",
    "stage": "prod"
  },
  "queryStringParameters": {
    "job_id": "6d94567b-04e2-4df0-bc10-d0b1a1f4d09f"
  }
}
```

Success response:

```json
{
  "ok": true,
  "connection_id": "abc123",
  "job_id": "6d94567b-04e2-4df0-bc10-d0b1a1f4d09f",
  "management_endpoint": "https://ws.example.org/prod"
}
```

Status codes:

| Status | Behavior |
| --- | --- |
| `200` | Connection state stored and stream task started. |
| `400` | Missing `connectionId` or `job_id`. |

### `POST /jobs/status/ws/ack`

Acknowledges a message sent over API Gateway websocket.

```json
{
  "connectionId": "abc123",
  "message_id": "70ec5c0f44dd4cf18a7d510489e03b1e"
}
```

Response:

```json
{
  "ok": true,
  "connection_id": "abc123",
  "message_id": "70ec5c0f44dd4cf18a7d510489e03b1e",
  "acknowledged": true
}
```

`acknowledged` is `false` when the connection or pending message does not match.

### `POST /jobs/status/ws/disconnect`

Removes an API Gateway connection and cancels its background status stream.

```json
{
  "connectionId": "abc123"
}
```

Response:

```json
{
  "ok": true,
  "connection_id": "abc123"
}
```

Status codes:

| Status | Behavior |
| --- | --- |
| `200` | Connection removed or stop requested. |
| `400` | Missing `connectionId`. |

### `POST /jobs/status/ws/default`

Default API Gateway route. If the route key resolves to `ack`, it delegates to the ack handler. Otherwise it returns a simple route acknowledgement.

Example response:

```json
{
  "ok": true,
  "route": "$default"
}
```

### API Gateway Stream Failure Behavior

| Failure | Behavior |
| --- | --- |
| Ack timeout | Deletes the API Gateway connection and removes local state. |
| `GoneException` | Logs that the connection is gone and removes local state. |
| Other client error | Logs the error and removes local state. |
| Internal exception | Attempts to post a `job_status_error` payload, deletes the connection, and removes local state. |

## `POST /jobs/results`

### Purpose

Returns result JSON for a specific NVFlare job/function/workflow combination, along with the function config used for that workflow.

### Request

```json
{
  "nvflare_job_id": "96b6f63e-0292-4f0e-bb64-a03b926b10bc",
  "function": "STAT_ANALYTICS",
  "workflow_id": "workflow_stat_analytics__cox_lasso"
}
```

`function` must be a valid `SupportedFunction` enum value.

`nvflare_job_id` must match `[A-Za-z0-9_-]+`. The value is used as a filesystem path component when result files are located, so the route rejects anything outside that charset before creating the retriever. `NVFlareJobsDataRetriever.__init__` enforces the same rule and raises `ValueError` for a missing or non-matching id.

### Success Response

```json
{
  "job_data": {
    "initiator_results": {},
    "aggregate_results": {},
    "aggregate_processed_results": {},
    "workflow_error": null,
    "paths": {
      "initiator_used": "/job-results/<job>/<computation>/<workflow>/initiator/raw_results.json",
      "aggregated_used": "/job-results/<job>/<computation>/<workflow>/aggregated/raw_results.json",
      "aggregate_processed_used": "/job-results/<job>/<computation>/<workflow>/aggregated/processed_results.json",
      "workflow_error_used": ""
    }
  },
  "function_config": {
    "model_key": "cox_lasso",
    "open_access": "true"
  }
}
```

The concrete result content depends on the runtime workflow output files. If a specific result file cannot be read, the corresponding section is returned as an object with an `error` string.

### Status Codes

| Status | Behavior |
| --- | --- |
| `200` | Result payload returned. |
| `400` | Missing `nvflare_job_id`, `function`, or `workflow_id`; `nvflare_job_id` outside `[A-Za-z0-9_-]+`; or unsupported function. |
| `500` | Result retrieval failed unexpectedly. |

Error bodies:

| Case | Response body |
| --- | --- |
| Missing `nvflare_job_id` | `{"error": "nvflare_job_id is required."}` |
| `nvflare_job_id` outside `[A-Za-z0-9_-]+` | `{"error": "Invalid nvflare_job_id."}` |
| Missing `function` | `{"error": "function is required."}` |
| Missing `workflow_id` | `{"error": "workflow_id is required."}` |
| Unsupported function | `{"error": "Unsupported function '<name>'"}` |
| Retrieval exception | `{"error": "Failed to fetch workflow data: [...]"}` |

### Taskflow Report Side Effect

After the response payload is assembled and before it is returned, the route calls:

```python
await asyncio.to_thread(
    taskflow_report.generate_report_for_job,
    nvflare_job_id,
    case_label=f"{function_name} ({nvflare_job_id})",
)
```

The call is wrapped in a bare `try`/`except: pass`, and `generate_report_for_job()` itself returns `None` instead of raising. Report generation therefore cannot change the status code or body of `/jobs/results`. The work is offloaded to a worker thread so the filesystem walk does not block the event loop.

`generate_report_for_job()` collects every `trace.jsonl` and `trace_filter.jsonl` written for the job under `DUALITY_NVFLARE_JOB_SAVE_LOCATION` and `DUALITY_NVFLARE_WORKSPACE`, merges them into one causal graph, and writes artifacts to:

```text
<DUALITY_NVFLARE_JOB_SAVE_LOCATION>/<nvflare_job_id>/taskflow/
```

Behavior notes:

- Generation is skipped when `index.json` or a `.no-trace` marker already exists in the output directory, so repeated result fetches do not rebuild the report.
- When no trace files are found, a `.no-trace` marker file is written so later fetches do not re-scan the workspace tree.
- The helper returns `None` when the job id is not id-safe, when neither root directory exists, when no job save location is configured, or when writing fails.

### Result File Lookup

`NVFlareJobsDataRetriever.retrieve_workflow_data(workflow_id)` builds this base path:

```text
<job-results-root>/<nvflare_job_id>/<computation_type>/<workflow_id>/
```

`computation_type` comes from `FUNCTION_TO_COMPUTATION_TYPE` for the supplied `SupportedFunction`.

The retriever reads local files when `EnvironmentProvider.get_env() == Environment.LOCAL`. Otherwise it uses `SSHConnectionProvider` and remote `cat`/`find` commands.

Result lookup behavior:

| Response Section | Lookup Order |
| --- | --- |
| `initiator_results` | `initiator/raw_results.json`, `initiator/results.json`, `client/*/error.json`, `local/local_results.json`, `local/error.json`. |
| `aggregate_results` | `aggregated/raw_results.json`, then `aggregated/results.json`. |
| `aggregate_processed_results` | `aggregated/processed_results.json`. |
| `workflow_error` | `error.json` at the workflow root, optional. |
| `paths` | Records the exact file path used for each readable section. |

### Local Result Root

For local mode, the result root is resolved in this order:

1. `DUALITY_NVFLARE_JOB_SAVE_LOCATION` when present.
2. `DUALITY_NVFLARE_WORKSPACE` or `/home/ubuntu/nvflare/workspace/duality_nvflare/prod_00`.
3. `DUALITY_NVFLARE_HOST` appended under the workspace.
4. `job-results` appended under the host path.

For non-local mode, the root is `NVFlareProvisionProvider.get_nvflare_instance().client_to_server_job_save_location` and files are read over SSH.

### Tables Read

| Table | Use |
| --- | --- |
| `nvflare_jobs` | Resolve config rows by NVFlare assigned ID. |
| `nvflare_job_function_configs` | Find function config set for `workflow_id`. |
| `defined_function_config_sets` | Config set join. |
| `defined_functions` | Match supplied function. |
| `defined_function_config_set_members` | Config set members. |
| `defined_function_config_properties` | Return property names/values. |

## NVFlare Monitor Status Updates

`NVFlareJobMonitor.wait_for_completion()` polls NVFlare admin with:

```text
list_jobs <nvflare_assigned_id>
```

The monitor parses table rows shaped like:

```text
| <job_id> | <name> | <status> | <submit_time> | <run_duration> |
```

For the matching job ID it:

1. Stores `submit_time` and `run_duration` on the monitor instance.
2. Calls `NVFlareJobsManager.set_nvflare_job_status(status)`.
3. Calls `NVFlareJobsManager.set_submission_timing(submit_time, run_duration)`.
4. Returns when the NVFlare status begins with `FINISHED:`.
5. Raises `TimeoutError` if the timeout expires before completion.

`set_nvflare_job_status()` checks the parent `job_runner_log` row before writing `nvflare_jobs.status`. If the job runner status is in `FAILURE_JOB_RUNNER_STATUSES`, the runner status overrides the requested NVFlare status. The current override set contains `JobRunnerStatus.THRESHOLD_NOT_MET`.

## Result Retrieval Error Handling

`NVFlareJobsDataRetriever` does not fail the entire results response for missing individual result files. It returns error strings inside the result sections. Examples:

| Condition | Returned Section Behavior |
| --- | --- |
| Missing file | Section becomes `{"error": "Unreadable file: <path> (not found)"}`. |
| Empty remote file | Section becomes `{"error": "Empty file: <path>"}`. |
| Invalid JSON | Section becomes `{"error": "Invalid JSON in <path>: ..."}`. |
| Missing optional workflow `error.json` | `workflow_error` becomes `null`. |
| Missing `profile_summary.json` | `profile_summary` is omitted from mapping response. |

Unexpected exceptions in the route layer return HTTP 500 with traceback lines in the `error` string.

## Frontend Usage Pattern

The expected frontend flow is:

1. Submit a job with `POST /nvflare/jobs/submit`.
2. Store the returned job runner `job_id`.
3. Stream status through websocket or poll `POST /jobs/status` using the job runner ID.
4. Watch `referenced_by` in the status payload for NVFlare assigned job IDs.
5. Use `POST /jobs/info` for normal in-app metadata lookup, or `POST /nvflare/jobs/results_context` when an external launch starts with only the NVFlare assigned ID and needs project/filter context.
6. Use `POST /jobs/results/mapping` with the NVFlare assigned ID and function to discover workflow IDs.
7. Use `POST /jobs/results` for each workflow ID to retrieve result JSON plus function config.
8. Use `POST /jobs/function/config` when the UI needs only configuration metadata.
9. Use `POST /nvflare/jobs/history` to populate historical job lists filtered by project, function, and date.

## Authentication and Security Assumptions

Most job status/history/result routes, including `/nvflare/jobs/results_context`, contain comments indicating they should be placed behind bearer-token protection, but the current backend route code does not enforce bearer-token authentication at these endpoints. The actual current behavior is route-level unauthenticated access unless an upstream proxy, API Gateway, ALB, or hosting layer adds authentication.

`/nvflare/client/emit_progress` and `/nvflare/jobs/audit/submit` implement password checks in non-local environments using the MySQL password from `ResourceConfigProvider.get_mysql_config()`. The status/history/result endpoints documented here do not perform the same password check.

## Troubleshooting

| Symptom | Likely Cause | Where to Check |
| --- | --- | --- |
| `/jobs/status` stays `QUEUED` with empty log | `job_runner_log` row has not been written yet, or wrong job runner ID is being used. | `job_runner_log.uuid`, backend logs from `JobRunnerService` and `JobStatusWriter`. |
| Status stream disconnects after first message | Frontend is not sending `ack` with the exact `message_id` within 5 seconds. | Browser websocket handling, backend ack timeout logs. |
| API Gateway websocket sends no updates | Missing/incorrect `connectionId`, `job_id`, or management endpoint; process-local connection state was lost after restart. | `/jobs/status/ws/connect` response, API Gateway integration payload, backend `_ACTIVE_API_GATEWAY_CONNECTIONS` logs. |
| Job history shows job but no results | NVFlare assigned job ID exists, but result files are not present under the expected job-results path. | `nvflare_jobs.output_path`, NVFlare server job-results directory, local `DUALITY_NVFLARE_JOB_SAVE_LOCATION`. |
| `/jobs/results/mapping` returns empty `workflow_dirs` | Computation directory is missing, function name maps to a different computation type, or job results are in a different root. | `FUNCTION_TO_COMPUTATION_TYPE`, job-results folder layout, environment mode. |
| `/jobs/results` returns per-section file errors | Expected raw/results/processed files are missing, empty, unreadable, or invalid JSON. | `initiator/`, `aggregated/`, `client/*/`, `local/`, and workflow root `error.json`. |
| Job history filtering returns too many jobs | `filter_mode` defaults to `ANY`; use `ONLY` to require exactly the supplied function set. | `/nvflare/jobs/history` payload. |
| Date filtering does not match expectation | `date_filter.mode` must be `ON`, `BEFORE`, or `AFTER`; fallback `create_date` is treated as `AFTER`. | `/nvflare/jobs/history` payload. |
| NVFlare job status is overridden | `NVFlareJobsManager.set_nvflare_job_status()` found a runner-level stop/failure status that takes precedence. | `job_runner_log.status`, especially `Threshold Not Met`. |
