The primary obstacle to parallelizing OpenFHE in Python stems from a conflict between Python's concurrency models and OpenFHE's internal architecture. First, standard multi-threading (`ThreadPoolExecutor`) proved ineffective because the OpenFHE bindings hold the **Global Interpreter Lock (GIL)** during execution. This forced threads to run sequentially, resulting in execution times (10–17s) that were slower than the serial baseline. Second, attempting to bypass the GIL using standard multiprocessing (`fork`) caused fatal deadlocks. OpenFHE uses **OpenMP** for internal threading, and when `fork()` copies the parent process's memory, it includes synchronization locks in their "locked" state but does not copy the threads holding them. Child processes subsequently freeze, waiting forever for non-existent threads to release these locks .

To resolve these issues, we adopted a **Spawn + Shared Memory** architecture. We switched the multiprocessing context to `spawn`, which creates fresh processes with a clean memory state, eliminating the OpenMP deadlocks. However, `spawn` does not inherit memory, so passing the massive cryptographic keys (23MB) to every worker initially caused a massive I/O bottleneck (~42s runtime). We solved this by serializing the keys once into **Shared Memory** (`multiprocessing.shared_memory`), allowing all workers to read the data instantly from RAM without copying . Finally, we applied **Throttled Parallelism** by injecting `OMP_NUM_THREADS=1` into the workers, preventing thread oversubscription. This strategy achieved a **2.3x speedup** (~4.5s runtime) and 100% stability, accepting a higher RAM footprint (~3.6GB vs 0.7GB) as the necessary trade-off for performance.
